RYUJIN AI — PROJECT DOCUMENTATION
====================================
Current checkpoint: Day 6 — Streaming Chat
This is the living engineering reference for the Ryujin AI project.

1. PROJECT GOAL
---------------
Ryujin AI is intended to become a production-style multi-agent AI workspace.

Core idea:
The user describes a task naturally. Ryujin's Supervisor decides which agent and
tools should handle the task, then executes the appropriate workflow.

Long-term:
User -> Streamlit -> FastAPI -> Supervisor -> Specialized Agent -> Subgraph
-> Tools/RAG -> Result -> Streaming -> Streamlit

Planned agents:
1. Research
2. Coding
3. Writing
4. Study
5. General Chat

5. CURRENT LANGGRAPH STATE
---------------------------
Current state:

class RyujinState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

State is the shared "backpack" containing messages.

add_messages merges new messages into the existing message list.

The state is intentionally minimal right now.

Possible future fields:
- current_agent
- files
- retrieved_context
- tool_results
- workflow/task status
- artifacts

Only add fields when needed.

6. CURRENT PERSISTENCE
----------------------
Persistence is currently conversation/thread scoped.

Example:

Chat A:
  thread_id = A
  history = A

Chat B:
  thread_id = B
  history = B

The LangGraph checkpointer stores graph state associated with thread_id.

Current architecture:

Main graph
   |
   v
SQLite checkpointer
   |
   v
thread_id
   |
   v
conversation state

IMPORTANT:
This is NOT global user memory.

If the user says in Chat A:
"My name is Eshan."

and creates Chat B, asking:
"What is my name?"

Chat B will not automatically know the answer simply because Chat A knew it.

That is expected under the current design.

7. CONVERSATION STATE VS GLOBAL MEMORY
--------------------------------------
These concepts must remain separate.

Conversation state:
What happened in one chat/thread.

Task/workflow state:
Where a particular workflow currently is.

Artifacts/results:
Outputs produced by previous tasks.

Global/user memory:
Facts or preferences intentionally available across chats.

Current Ryujin has conversation state through thread_id/checkpointing.
Global memory is planned for later.

9. EXACT QUERY FLOW
-------------------
Example:
User types: "Explain LangGraph simply."

STEP 1 — User input
The Streamlit chat input receives the prompt.

If there is no active conversation, create_conversation() creates a UUID thread_id.

The user message is added to the frontend conversation.

pending_prompt is set.
is_generating is set to True.

A Streamlit rerun occurs.

STEP 2 — Render current chat
Streamlit renders the sidebar, header and current conversation.

render_chat() reads the active thread and its messages.

Empty messages are skipped so stale empty assistant placeholders are not shown.

STEP 3 — Process pending prompt
process_pending_prompt() sees that generation is active and retrieves:
- prompt
- current conversation
- thread_id

STEP 4 — Call streaming API
frontend/utils/api.py sends:

POST http://127.0.0.1:8000/chat/stream

JSON:
{
    "message": "...",
    "thread_id": "..."
}

The request uses stream=True.

STEP 5 — FastAPI
The /chat/stream route receives ChatRequest and returns StreamingResponse.

STEP 6 — Backend service
chat_service.stream_chat() creates the LangGraph config:

{
    "configurable": {
        "thread_id": thread_id
    }
}

It calls chat_graph.astream() with a HumanMessage and:
stream_mode="messages"

STEP 7 — LangGraph
Current graph:

START
  |
  v
chat_agent
  |
  v
END

chat_agent calls ChatOpenAI.

The thread_id is used with the checkpointer for conversation state.

STEP 8 — Backend yields chunks
The backend extracts message_chunk.content and yields it.

FastAPI sends the chunks progressively.

STEP 9 — Frontend receives chunks
api.py uses requests.iter_content() and yields each non-empty chunk.

STEP 10 — Streamlit displays chunks
chat_processor.py uses:

with st.chat_message("assistant"):
    response = st.write_stream(...)

The user sees the response progressively.

STEP 11 — Save completed response
After streaming finishes, the completed response is appended:

{
    "role": "assistant",
    "content": response
}

Then:
pending_prompt = None
is_generating = False

The input becomes available again.

10. STREAMING — WHAT CHANGED ON DAY 6
--------------------------------------
Before:

User -> request -> wait for full LLM response -> display answer

After:

User -> request
          |
          v
      LLM/LangGraph
          |
       chunks
          |
          v
       FastAPI
          |
       chunks
          |
          v
      Streamlit
          |
          v
  progressive answer

Streaming makes the UI responsive because the answer is displayed while it is
being generated/transferred instead of waiting for the entire response.

Frontend now uses /chat/stream.

12. STREAMLIT RENDERING ISSUE AND FIX
-------------------------------------
During Day 6, the streamed answer initially had a quick stutter/jump and the
input sometimes became difficult to interact with.

An earlier implementation:
1. Added an empty assistant message to conversation state.
2. Created another live assistant container for streaming.
3. Called st.rerun() after streaming.

This caused duplicate/empty assistant containers and extra rendering.

The stable approach:
- Do not append an empty assistant placeholder before streaming.
- Stream directly inside st.chat_message("assistant").
- Save only the completed assistant response.
- Avoid an unnecessary final full-page st.rerun().
- chat.py skips messages whose content is empty.

This made the chat UI stable.

17. SUPERVISOR DESIGN
---------------------
Supervisor is an LLM-based router/orchestrator.

Supervisor answers:
"WHO should handle this task?"

LangGraph executes the decision.

Important:
LLM = decision maker
LangGraph = workflow controller

A possible future structured decision:

- new_task
- continue_task
- answer_hitl

- writing
- research
- coding
- study

- explanation

use_previous_context:
- whether relevant prior context/artifacts should be used

Exact schema can evolve later.

18. NEW TASK VS CONTINUATION
----------------------------
Agents do not own the conversation.

A follow-up should be interpreted using the current conversation/context.

Example:
User: "Write an email to my manager."
Writing workflow completes.

Later:
"Write it again but make it shorter."

This should normally be a new execution using previous context/output.

A completed workflow should not automatically restart just because the user
references its result.

Example:
"Let's post the email you provided."

Supervisor should interpret the reference and route the new action appropriately.

19. HITL
--------
Human-in-the-loop is separate from ordinary continuation.

If a workflow pauses for approval:

Workflow -> WAIT -> User approval -> Resume same workflow

If the user starts a different task while another workflow is paused, the
pending workflow remains paused.
